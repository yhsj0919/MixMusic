# HyperQueue

2026-10-16：独立的泛型惰性队列，位于 `lib/common/queue`。它不是 UI 控件，不依赖歌曲、插件、播放或下载实现。

播放控制器和下载控制器已替换为 `HyperQueue<T>`；播放模式、播放引擎、音质解析、下载执行仍由各自控制器处理。

## 对外操作

```dart
queue.append(item);
queue.appendCollection(source);
queue.insertNext(item);
queue.insertNextCollection(source);
queue.remove(index);
queue.removeCollection(source.key);
queue.suspend(source.key);
queue.resume(source.key);
queue.clear();
```

构造时提供身份比较 `same` 和入队快照 `snapshot`。`HyperQueueSource<T>` 接收来源标识、标题、已加载内容、是否还有下一页、错误状态和 `loadMore`。播放端直接连接现有集合控制器，共享页面已经加载的结果和请求，不重复维护分页索引。

- `items`：目前已展开的条目，供既有歌曲列表和系统媒体队列使用；它不等于完整逻辑队列。
- `entries`：展示条目及尚未展开完的来源占位；未加载的歌单加入后立即可见。
- `roots`：顶层条目与来源，完整加载后仍保留分组；`itemsIn(key)` 获取来源内部已展开条目，供下载分组展示和取消使用。
- `index`：当前已展开条目的索引，分页插入时维持当前条目的位置。
- `nextIndex()`：按逻辑顺序查找下一项，遇到未展开来源先加载，失败不越过。
- `loadMore()`：临近末尾两首时请求一页；`viewing: true` 用于查看队列时展开最靠前的未完成来源，`retry: true` 显式重试。

## 顺序约定

```text
歌单 A（100 首，已加载 20 首） → 单曲 → 歌单 B（尚未加载）
```

加入 B 只登记来源，不立即请求。A 后续分页仍填入 A 内部，始终排在追加单曲和 B 前面。A 的未加载部分是顺序屏障，不能因 B 已在详情页加载而自动跳过去。

“下一首”插入当前条目之后，支持单项和整个来源；插入来源结束后回到原来的后续条目。来源保留各自加载状态，不共用或重置分页索引。全局去重遵循构造时提供的身份规则，已消费的分页结果不会因后续追加而重新加入已移除条目。

分页请求合并，失败保留来源并停止自动重试。清空、移除来源或停用插件后解除订阅；旧请求可继续为详情页提供结果，但不能重新填充队列。

随机播放仍从当前已展开歌曲中选择，不为全量随机拉完整歌单；播放顺序策略不放进 HyperQueue。UI、系统媒体队列显示的歌曲数量也是已展开数量，来源占位不伪装成歌曲。

下载任务列表使用同一队列容器。`blockedSource` 标识本次分页失败的来源；`suspend/resume` 保留内容与分页状态，挂起后顺序消费跳过整个来源，`entries` 仍显示挂起记录。下载控制器决定重试次数和何时挂起，HyperQueue 本身不自动重试或跳过。集合分页消费、失败隔离、详情页批量入口和下载分组已接通，缓存复制已接通，任务持久化仍待补齐。

仅进行功能测试和静态检查，不做 UI 验证。平台设备实测仍列为待验证。

本次验证：73 项业务功能回归、5 项 Windows 原生 MPV 测试通过，静态检查通过。专门覆盖 100 首 A 仅加载 20 首后追加单曲和 B、下一首插入整个 B 后回到 A、同页并发合并、失败保留屏障、清空不回填及插件停用。原生测试使用空音频输出，不等于设备听测。
