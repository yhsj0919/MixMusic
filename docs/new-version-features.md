# MixMusic 新版功能规划

> 状态：讨论稿  
> 更新日期：2026-08-19

## 1. 产品定位

新版 MixMusic 延续现有插件化播放器架构，引入 Lemon JS 相关能力。

- 宿主负责稳定、统一的页面和音乐播放体验。
- 插件负责提供音源及与具体平台相关的业务能力。
- 软件本身不内置在线音源，在线内容与播放资源由插件提供。
- 在保留现有功能的基础上，补全“我的”、评论、收藏、批量下载、跨设备和同步能力。

暂不采用“由插件自由实现整个应用 UI”的方案。宿主仍然负责主要页面，避免不同插件造成交互割裂，并保证手机、平板、桌面和车机上的一致性。

新版在当前仓库内全新重写，完成后覆盖当前实现，或在切换前将当前版本改名保留。新版不兼容旧版代码、数据库、设置或旧插件，不为旧版提供迁移和兼容层。

## 2. 架构边界

新版基础技术约定：

- 路由统一使用 `go_router`，不再混用 GetX 路由或其他并行路由体系。
- 状态管理统一使用自研的 `lemon_x`。
- 页面统一使用自研的 `lemon_ui`，覆盖手机、平板、桌面和车机。
- 旧版中的技术混用属于项目长期演进结果，不作为新版风格和架构参考。
- 旧版手机与桌面页面风格不一致，是分别采用不同 UI 技术导致的历史结果，不作为新版设计方向。
- 旧代码主要用于参考业务逻辑、插件思路、数据模型和简洁的代码表达方式。

新版页面共享同一套结构、状态和业务组件，通过 `lemon_ui` 的响应式布局适配不同屏幕；只有导航位置、窗口布局、输入方式等真实平台差异才采用条件布局，不再分别维护两套功能页面。

### 2.1 平台支持顺序

首批开发和验收平台：

- Android。
- Windows。
- 车机，作为独立的大屏、横屏和车载交互形态适配。

后续支持：

- iOS。
- macOS。
- Linux。
- Web。

最后评估和支持鸿蒙。首批架构不依赖 Android 或 Windows 专属业务实现，通用模型、插件协议、状态和页面结构保持跨平台；平台差异集中在应用配置、系统能力适配和 `lemon_ui` 响应式布局中。

### 2.2 宿主负责

- 首页、搜索、我的、详情页和设置页等统一页面。
- 播放页面、播放队列和全局播放控制。
- 本地播放器及系统媒体控制。
- 本地资料库、收藏、歌单和播放历史。
- 下载任务、离线文件和缓存管理。
- 跨站点匹配与播放失败后的自动换源流程。
- 插件安装、更新、启用、停用、卸载和权限管理。
- 统一的数据模型、持久化和跨设备同步模型。
- 手机、平板、桌面和车机的自适应体验。

### 2.3 插件负责

- 音源数据和播放资源。
- 平台登录的完整业务流程。
- 登录后的平台用户信息、歌单、收藏和关注等远端数据。
- 平台评论数据及相关操作。
- 插件自身需要的设置和平台特有能力。

宿主不再实现 Cookie、手机验证码、网页、密码或扫码等具体登录流程。插件自行实现登录，但凭据的安全存储、WebView 等基础设施仍由宿主提供受控接口。

- 播放队列和播放历史。
- 歌词显示。
- 定时关闭。
- 播放音质选择。
- 歌曲下载。
- 歌单分类、列表和详情。
- 专辑分类、列表和详情。
- 歌手列表、歌曲和专辑详情。
- 单曲、歌单、专辑、歌手和 MV 搜索。
- 榜单、新歌和每日推荐。
- MV 分类、详情和播放。
- 歌单链接导入和解析。
- 首页数据源配置。
- 跨站点歌曲和歌词匹配。
- 插件安装、删除、查看和在线插件列表。
- 手机、桌面、平板和车机 UI。

现有登录功能不作为宿主功能保留，而是迁移到新版插件接口。

## 4. 新版核心功能

### 4.1 “我的”与本地资料库

“我的”由宿主统一实现，聚合本地数据与各插件提供的远端数据。

- 本地收藏。
- 本地歌单。
- 最近播放。
- 下载内容。
- 本地音乐。
- 已登录平台。
- 平台收藏、平台歌单和关注内容。
- 云端或同步服务中的资料库。
- 当前设备及其他播放终端。

远端歌单可支持以下关系，具体首版范围待定：

- 远端快捷入口：由插件实时读取。
- 导入本地副本：导入后与原平台独立。
- 双向同步：本地修改同步回平台。

#### 本地音乐的实现边界与阶段

本地音乐采用“宿主核心 + 插件扩展”，不要求用户安装 JS 插件才能播放本地文件。

- 音乐文件夹在设置中统一管理，支持多个目录并保存配置；移除目录只取消关联，不删除文件。Android 使用系统目录授权并保留访问权限，Windows 保存目录路径。
- 基础阶段只按需逐层浏览，不递归扫描全部目录；文件可直接播放或加入统一队列，完整本地首页在音乐库索引阶段接入。
- 宿主负责文件与文件夹选择、系统权限、本地播放、元数据读取、内嵌封面与歌词，以及后续目录扫描、索引和文件变更检测。
- 本地音源使用内置 Dart/平台能力，向统一页面与播放队列提供相似业务接口，不伪装成 JS 插件。
- 身份保持来源标识加不透明 ID，不增加资源 type；文件路径不直接作为数据库主键。
- 插件扩展 WebDAV、网盘、NAS 等远程文件来源，以及歌词、封面、歌曲信息和在线资源匹配。WebDAV 同步后端的实现归属仍单独待定。
- 基础本地播放放在播放队列和在线详情之后、数据库之前：先支持选择文件或文件夹、读取歌曲信息、加入内存队列和播放，不依赖数据库。
- 本地音乐库随数据库阶段实现：目录扫描、增量更新、搜索分类、本地收藏和歌单；在线匹配后续接入。本地收藏、历史及歌单持久化整体后置，不阻塞正常听歌。
- 下载后的歌曲复用相同本地播放能力，不再另做一套播放流程。
- 本地音乐不只是文件选择入口，而是与插件音源并列的内置音源。统一首页、专辑、歌手、歌单、歌曲列表和详情入口的视觉与交互，数据获取由不同音源实现。
- 本地首页提供专辑、歌手、歌单等浏览分区；在线首页“新歌”分区在本地对应“最近添加”，不将导入时间当作发行时间。不支持的分区隐藏，不保留空占位。
- 页面与在线详情阶段先确定可共用的入口和页面结构，不提前构建依赖扫描的本地首页；数据库与本地音乐库阶段完成扫描、标签归类和索引后，再接入完整本地首页。基础本地播放仍可独立提前完成。

### 4.2 收藏

收藏默认保存歌曲原始插件和平台 ID，不在收藏时主动匹配其他站点。

- 收藏到 MixMusic 本地资料库。
- 通过插件收藏或取消收藏到对应平台。
- 将多个平台的收藏展示在统一“我的”页面。
- 插件卸载或暂时失效时保留歌曲显示快照。
- 重新安装相同插件 ID 后恢复资源解析能力。
- 支持批量收藏和批量取消收藏。

#### 收藏目标与交互

收藏目标支持：

- 收藏到当前平台，由音源插件执行远端收藏。
- 收藏到 MixMusic，进入本地统一收藏库。
- 同时收藏到当前平台和 MixMusic。

暂定交互规则：

- 普通点击收藏按钮时，按照全局收藏默认设置执行。
- 初始默认目标为当前平台。
- 用户尚未设置默认行为时，可以弹窗选择收藏目标，并允许记住本次选择为全局默认。
- 长按收藏按钮时始终打开目标选择，不改变普通点击的快捷性。
- 设置中可以随时修改默认收藏目标。
- 平台收藏需要登录或交互时，由对应插件返回并启动登录 Flow。
- 平台不支持收藏时，弹窗中不显示或禁用该目标，并允许收藏到 MixMusic。
- 无论收藏到哪个目标，歌曲仍保留原始 `pluginId + id` 身份。

#### 跨站点收藏播放策略

1. 收藏 A 音源的歌曲时，仅记录 A 的资源信息。
2. 下次播放时继续优先使用 A。
3. A 短暂异常时先进行有限重试。
4. A 确认无法播放后，再调用其他音源插件匹配。
5. 只自动播放高置信度的匹配结果。
6. 中等置信度的结果交由用户选择。
7. 匹配成功后可缓存为备用来源，但不改变原收藏身份。
8. 用户可以手动固定、删除或重新匹配备用来源。

此策略称为“惰性匹配”或“按需换源”。暂不在收藏时同时匹配所有可用资源。

### 4.3 评论

- 歌曲评论。
- 歌单、专辑和 MV 评论，可根据插件能力提供。
- 热门评论和最新评论。
- 分页加载。
- 评论用户信息。

首版建议优先实现评论读取。点赞、回复、发布和删除评论可在后续完善。

### 4.4 批量下载

支持从以下入口创建批量下载任务：

- 批量选择歌曲。
- 下载整个歌单。
- 下载整个专辑。
- 下载收藏列表。
- 下载播放队列。
- 下载歌手热门歌曲。
- 仅下载尚未离线的歌曲。

下载选项包括：

- 指定音质或自动选择最佳可用音质。
- 原音源失败后是否允许自动换源。
- 是否下载封面、歌词、翻译歌词和逐字歌词。
- 是否写入音乐文件标签。
- 下载目录和文件名规则。
- 同名文件处理方式。
- 最大并发任务数。
- 仅在 Wi-Fi 下下载。
- 电量和剩余存储空间限制。

任务管理包括：

- 暂停、继续、取消和重试。
- 全部暂停和全部继续。
- 断点续传。
- 失败自动换源。
- 临时 URL 过期后重新向插件解析。
- 下载失败原因和需要人工确认的匹配结果。
- 下载完成后自动加入本地资料库。

默认下载策略为：优先原音源，原音源失败后按设置尝试其他音源。实际下载来源不会修改歌曲的原收藏来源。

#### 音乐播放缓存

缓存用于复用已经收听的网络音频，避免每次播放都重新下载；属于宿主通用播放能力，不识别插件的数据来源。普通完整资源的首版已实现，分段复用等仍为后续规划，详见 [缓存说明](music-cache.md)。

- 设置中提供音乐缓存开关、容量上限、已用空间、手动清理和日志入口。首版默认开启、512 MB。
- 缓存身份使用 `pluginId + 原始动态歌曲 ID + 音质`；动态 ID 使用统一规范化索引，仍原样传给插件。不使用临时 URL 作为身份，URL 变化或过期不影响已有缓存。
- 同一歌曲、同一音质再次播放，优先使用有效的完整本地缓存，不再调用播放地址解析接口或请求网络音频；歌词获取仍独立处理。
- 切换音质不复用其他音质的音频；先查找新音质的缓存，未命中才解析并请求网络。旧音质缓存不因切换立即删除，切回时仍可复用。
- 缓存记录实际返回的音质。插件未确认实际音质时，不把不同音质请求静默归并，不用低音质文件冒充高音质。
- 未命中时正常网络播放，尽量复用本次播放的数据写入磁盘，不另发一次全量下载请求；不因为开始播放就主动拉完整首或预取整个歌单。
- 区分完整缓存与临时片段。跳转产生的缺口和中断文件不能标记为完整缓存；完整性以实际接收全部文件为准，不以是否听完为准。首版不合并部分 Range，不缓存未知长度和分段流。
- 同一缓存键合并重复写入，完整文件确认后再登记可复用状态；损坏、缺失或用户主动刷新时才重新请求，正常命中不先联网检查。
- 容量不足时优先清理最久未使用的缓存；不删除正在使用的文件，手动清理中的占用文件延后处理。
- 缓存与正式下载分开管理：缓存可自动淘汰，用户下载的文件不因缓存清理而删除，也不把缓存自动列入本地音乐库。
- 首版仅用于本机播放，音量、倍速和均衡器变化不影响缓存身份；更换插件或资源 ID 不自动复用旧来源音频。

首版采用宿主本机 HTTP 转发，在同一次 MPV 播放请求中写入完整文件，不修改第三方音频库。独立索引保存设置、大小及最近使用时间；控制台与日志弹窗可检查是否写入和命中。播放器正常预读可能提前接收完整歌曲，这不属于额外下载任务。

### 4.5 跨设备与同步

- 在多个 MixMusic 客户端间同步本地收藏和本地歌单。
- 同步播放历史和播放进度。
- 同步歌曲的备用来源映射。
- 同步部分应用及插件设置。
- WebDAV 作为优先考虑的同步后端。
- 后续可扩展到其他云存储、自建服务和局域网直连。
- 同步采用数据记录和变更合并，不直接覆盖整个数据库文件。

### 4.6 播放终端

计划提供可扩展的播放终端能力，统一控制本机或其他设备播放。

- 本机播放。
- 委托另一台 MixMusic 设备播放。
- 智能音箱或局域网设备播放。
- 后续评估 DLNA、Chromecast、AirPlay 或其他协议。
- 发现设备、连接、断开和设备状态显示。
- 播放、暂停、停止、进度、音量和队列控制。

需要支持两类远程终端：

- 远程控制型：终端自行解析并播放资源。
- 媒体投送型：宿主解析 URL 或提供受控媒体代理后交给终端播放。

播放终端是否作为 Lemon JS 插件能力开放，以及首版开放到什么程度，暂未最终确定。

### 4.7 虚拟播放队列与惰性集合加载

歌单、专辑、榜单和歌手歌曲等集合采用分页接口。新版不在“播放全部”或“添加全部”时自动拉取全部分页，避免无效请求，并降低第三方平台限流、验证码及账号或 IP 风控风险。

- 添加集合时保存插件 ID、集合动态 ID、当前已加载歌曲、下一页参数和加载状态，不立即展开完整集合。
- 复用详情页已经加载的数据，避免重复请求。
- 用户查看队列并滚动接近底部时按需加载。
- 用户不查看队列时，仅在顺序播放到已加载部分倒数一至两首时预取下一页。
- “提前一至两首”表示触发时机，实际请求仍遵循插件的分页大小。
- 页面关闭后停止浏览触发的加载，但保留播放所需的预取。
- 详情页、队列和播放预取共享分页缓存并合并相同请求。
- 同一插件限制请求并发，同一集合同时只允许一个分页请求。
- 请求失败采用退避策略；遇到限流、验证码、登录失效或风控错误时停止自动加载并提示用户。
- 清空队列或删除集合节点时取消对应请求；加载失败时保留已经加载的歌曲并允许重试。
- 顺序播放完整支持惰性加载；随机播放默认只作用于已加载歌曲。只有用户明确要求完整随机时才加载完整集合。
- “下载全部”是明确需要完整集合的独立任务，但仍须遵守插件请求频率与风控限制。

该方案称为“虚拟播放队列”或“惰性集合加载”，替代添加后在后台拉取完整歌单的方案。

### 4.8 音频系统

新版音频系统采用已经创建的 `lemon_audio` 兼容层，并在实际开发时接入封装好的 MPV 播放器。

- MPV 封装负责实际解码和播放。
- MixMusic 实现播放队列、歌曲解析、换源和产品状态。
- MPV 适配器实现 `LemonAudioPlayer`。
- `lemon_audio` 负责系统媒体通知、锁屏信息、媒体按键、蓝牙和车机控制、音频焦点与系统中断。
- 播放引擎的状态、进度、缓冲、时长和队列索引通过适配器上报给 `lemon_audio`。
- MixMusic 不再直接依赖 `audio_service`、`audio_session` 或各桌面系统媒体控制实现。
- `lemon_audio` 不负责业务队列、音源解析、跨站匹配或歌曲数据库。

关系如下：

```text
MixMusic 播放业务与虚拟队列
        ↓
封装好的 MPV 播放器
        ↓ LemonAudioPlayer 适配器
lemon_audio
        ↓
通知 / 锁屏 / 媒体键 / 音频焦点 / 系统中断
```

### 4.9 歌词系统

新版歌词统一使用本地项目 `lemon_lyric`，不继续使用旧版 `flutter_lyric` 或保留旧歌词实现。

`lemon_lyric` 已经具备普通歌词、逐字歌词、翻译等主要功能，基础歌词没有性能问题。当前卡顿仅针对 Canvas 版本；简单播放页先使用普通歌词视图，不因 Canvas 问题阻塞接入，也不重写已有数据能力。

实施顺序：

1. 保留现有普通歌词、逐字、翻译等解析和数据能力。
2. 定位 Apple Music 风格下滚动、逐字高亮、缩放、模糊、布局或重绘造成的性能问题。
3. 将时间进度、当前行状态和视觉动画的更新范围缩小到必要组件。
4. 在 Android、Windows 和车机上验证长歌词、逐字歌词与持续播放性能。
5. 基础性能稳定后，再继续完善 Apple Music 风格的细节表现。

首版歌词实现保持简单：

- 播放进度更新不应导致整个歌词页面重建。
- 只更新当前行和必要的可见区域。
- 歌词解析结果应复用，不在每次进度变化时重新解析。
- 动画和模糊等效果不能阻塞滚动与播放控制。
- 优化以保留 Apple Music 风格目标为前提，不因卡顿问题重新实现已经具备的歌词数据能力。
- 性能问题解决前，可以暂时关闭代价较高的视觉效果，但不删除逐字和翻译等功能。

## 5. Lemon JS 插件设计

### 5.1 插件形态

整体插件业务逻辑与当前版本相近，音源插件仍是主要插件形态。`lemon_js_extensions` 是专门为 MixMusic 新版准备的插件基础设施，是新版既定组成部分，不是候选依赖。插件安装、Session、运行时和 UI 组合全部建立在它之上，MixMusic 不重复实现通用插件管理框架。

新版采用混合插件模式：

- `service` 提供标准音乐数据和平台业务逻辑。
- JSUI routes/flows 提供登录、验证、首次配置等无法统一的交互。
- 宿主继续使用原生 `lemon_ui` 页面展示首页、搜索、歌单、专辑、歌手、评论和播放等标准内容。
- 同一插件的 service 与 JSUI 共享插件身份、Session、权限和隔离存储。
- 插件以 manifest 中实际声明的 service、UI 和 flow 能力为准，不设置互斥的固定插件类型。

首版优先支持用户从本地文件安装统一插件包。网络仓库、在线更新和其他安装来源可在本地安装流程稳定后接入。

统一插件包以 manifest 为入口，可包含：

```text
manifest.json
service/
  main.mjs
ui/
  authentication.mjs
assets/
```

裸单文件 JS 插件理论上可以支持，但暂未确定是否作为正式分发格式。推荐方案是：正式插件使用带 manifest 的统一包；如果后续保留单文件导入，则由宿主在安装时包装成统一插件包，而不在运行和管理层维护第二套插件模型。

对于多种插件类型，目前倾向使用“插件声明能力”的设计，而不是定义互斥的插件类别。一个插件包可以按需声明一个或多个能力，例如：

- 音源。
- 登录。
- 远端资料库。
- 评论。
- 播放终端。
- 同步存储。
- 元数据。
- 导入导出。

是否在首版支持音源之外的所有能力仍需继续评估。

### 5.2 UI 能力

宿主默认实现统一页面。暂不确定是否允许插件完全自定义播放页面。

推荐优先考虑受控的播放页扩展区域：

- 背景视觉效果。
- 封面区域。
- 歌词渲染器。
- 音频频谱和可视化。
- 歌曲附加信息。
- 播放页附加操作。

播放控制、进度条、播放队列和终端选择仍由宿主管理。是否开放完整播放页面替换能力列为待决定事项。

### 5.3 登录能力

- 登录业务完全由插件实现。
- 插件可以组合输入框、按钮、二维码、WebView 等宿主能力完成登录。
- 登录方式不由宿主枚举，插件可自行实现 Cookie、验证码、扫码、密码、OAuth 等流程。
- 宿主提供受控、安全的凭据存储。
- 账号凭据不能使用普通明文插件存储。
- 多账号支持作为后续详细设计内容。

### 5.5 音乐插件 API

新版音乐 API 的业务范围和方法语义尽量保持与当前版本一致，继续覆盖搜索、推荐、歌单、专辑、歌手、榜单、MV、播放地址、歌词、下载和用户数据等能力，但不保留旧运行时造成的字符串调用限制。

- JS service 使用明确导出的模块函数实现音乐协议。
- Dart 业务层提供类型明确的音乐插件接口，例如 `searchSong`、`playlistDetail`、`playUrl` 和 `lyric`。
- 页面、状态和播放器只调用 Dart 音乐接口，不直接书写 JS 方法名字符串。
- `lemon_js_extensions` 与 JS 模块之间仍可在底层按 export 名称分发调用，但字符串集中在协议适配边界。
- 方法是否可用由 manifest 的 contract 与接口约束确认，不由页面运行时探测方法名。
- 旧 API 可以调整不合理的命名和参数，但优先保持插件作者熟悉的业务结构。

示意：

```dart
abstract interface class MusicPlugin {
  Future<Page<Song>> searchSong(String keyword, PageRequest page);
  Future<Page<Song>> playlistDetail(Playlist playlist, PageRequest page);
  Future<Song> playUrl(Song song);
  Future<Lyric> lyric(Song song);
}
```

内部适配器负责把这些调用映射到当前插件的 Lemon JS service export。该接口用于消除业务代码中的字符串调用，不扩展成多层 UseCase 或通用 RPC 框架。

### 5.4 插件管理与安全

- 本地文件或 URL 安装插件。
- 插件仓库和更新检查。
- 启用、停用和卸载。
- API 版本与应用兼容性检查。
- 权限声明和安装前确认。
- 网络域名、文件、WebView、凭据、播放器控制等权限隔离。
- 插件错误、超时和崩溃隔离。
- 插件日志和开发者调试能力。
- 插件 ID 发布后保持稳定，升级不能修改插件 ID。

## 6. 资源 ID 约定

新版沿用现有设计：每种资源模型通过 `pluginId/package + id` 标识对应平台资源。

- 不增加资源 `type` 字段，不同资源由不同接口和模型区分。
- `id` 是插件定义的不透明动态值。
- `id` 可以是字符串、数字、数组或对象。
- 宿主不解析、不修改 ID 的业务含义。
- 宿主原样持久化，并在调用插件时原样传回。
- ID 必须能够安全序列化和反序列化。
- 超过 JavaScript 安全整数范围的数字 ID 应由插件使用字符串表达。

新版需要统一当前代码中 `id == id` 与 `id.toString() == id.toString()` 混用的问题，提供统一的动态 ID 比较与索引机制，但不改变插件协议。

## 7. 关系型数据库方案

动态 ID 不直接作为关系型数据库的主键。数据库使用本地生成的主键建立关系，同时保存插件资源身份。

数据库具体库暂未确定。新版本地存储属于核心能力，选型应优先满足实际查询与替换需求，而不是优先考虑 ORM 形式。

首批需要持久化的数据包括：

- 播放历史及最后播放时间。
- 本地收藏。
- 本地歌单、歌单顺序和歌曲关系。
- 插件资源快照。
- 跨站备用来源映射。
- 下载任务与本地文件记录。
- 虚拟队列及必要的恢复状态。
- 跨设备同步所需的修改时间或变更信息。

数据库需要重点支持：

- 按本地主键快速查询。
- 按 `plugin_id + external_key` 查询资源。
- 查询歌单中的歌曲并保持顺序。
- 插入、更新、替换和删除歌单内容。
- 批量插入和批量替换。
- 播放历史按时间排序、分页和限制数量。
- 收藏、下载和来源映射的关联查询。
- 事务，保证歌单批量替换等操作不会只完成一部分。
- 后续可维护的 Schema 迁移。

选型原则：API 简单直接、查询清晰、支持事务和迁移、不过度生成 DAO/Repository 层。开发初期可以直接使用具体数据库类和少量查询方法，等真实重复出现后再抽象。

### 7.1 两层身份

- 外部身份：`pluginId + dynamic id`，用于与插件通信。
- 内部身份：数据库生成的 `local_id`，用于主键、外键和关系查询。

歌曲、歌单、专辑等资源分别存储，因此不需要在身份中增加资源类型。

### 7.2 资源表基本字段

每类资源表至少保存：

- `local_id`：本地数据库主键。
- `plugin_id`：插件 ID。
- `external_id`：原始动态 ID 的 JSON。
- `external_key`：规范化动态 ID 后生成的稳定索引。
- 标题、封面等必要显示快照。

同类资源通过 `plugin_id + external_key` 建立唯一约束。

`external_key` 仅供宿主内部使用，插件仍然只接收原始 `id`。生成时应区分字符串和数字，递归规范化数组，并对对象字段排序，避免对象字段顺序导致同一 ID 产生不同索引。

### 7.3 歌单关系

- 歌单使用独立本地主键。
- 歌曲使用独立本地主键。
- 歌单与歌曲通过 `playlist_items` 关联表连接。
- 关联表保存歌曲顺序和加入时间。
- 是否允许同一歌曲在同一歌单中重复出现由产品规则决定。
- 本地歌单没有远端插件身份；远端歌单保存对应的 `plugin_id` 和动态 ID。

### 7.4 收藏、备用来源和下载关系

- 收藏表关联歌曲的本地主键。
- 跨站备用来源表关联原歌曲与替代歌曲的本地主键。
- 备用来源记录匹配置信度、验证时间、最后成功时间和用户确认状态。
- 下载任务关联用户选择的原歌曲。
- 自动换源下载时，另外记录最终实际提供资源的歌曲。
- 换源不会修改收藏和歌单中的原始资源身份。

## 8. 其他候选扩展

以下功能有价值，但暂未确定首版范围：

- 本地音乐扫描、标签读取和在线元数据补全。
- 元数据插件：封面、歌词、翻译、逐字歌词和音乐资料。
- 歌单导入导出插件：M3U、JSON、CSV 和其他播放器备份。
- 平台歌单双向同步。
- 评论发布、回复、点赞和删除。
- 自动化：定时同步、收藏后自动下载、根据网络切换播放终端等。
- 插件命令：换源、补全封面、导出队列、打开平台页面等快捷操作。
- 完整自定义播放页面。
- NFC“贴一贴”快捷操作：通过 NFC 标签触发播放歌曲或歌单、继续播放、切换播放终端，或执行插件注册的快捷命令。该能力作为候选插件功能记录，不承诺实现；平台支持范围、后台唤起、标签写入、权限与安全边界仍需评估。
- 桌面歌词：在桌面独立悬浮显示当前歌词，可选锁定、透明度、字体和逐字效果。
- 任务栏歌词：在平台能力允许时，将当前歌词或播放信息显示到任务栏相关区域。
- 小窗播放：提供轻量的封面、歌词和基础播放控制小窗。
- 桌面背景：使用封面、主题色、动态效果或歌词生成桌面播放背景。

桌面歌词、任务栏歌词、小窗播放和桌面背景属于后期产品亮点，不是首版必须功能，也不作为新版基础架构的强制要求。实现时应复用宿主现有播放状态、歌词数据和控制接口，不为这些候选功能提前增加主播放链路的复杂度。平台不支持时可以不实现，不要求所有平台行为完全一致。

## 9. 当前已确定的原则

1. 整体架构与当前版本相近。
2. 音源由插件提供，主要页面由宿主统一实现。
3. 登录业务迁移到插件，宿主不再管理具体登录方式。
4. 新版引入 Lemon JS 插件能力。
5. 保留当前功能，并补全“我的”、评论、收藏、批量下载和跨设备能力。
6. 资源继续使用 `pluginId/package + dynamic id`，不增加 `type`。
7. 收藏时不主动跨站匹配，原音源失败时才按需匹配其他音源。
8. 匹配到的其他音源是备用来源，不改变原收藏身份。
9. 关系型数据库使用本地主键建立歌单、收藏、下载和来源映射关系。
10. 播放终端插件、同步插件和完整自定义播放页面仍需继续讨论。
11. 集合加入播放队列后采用惰性加载：查看时滚动加载，播放接近已加载末尾时提前一至两首预取，不默认拉取完整集合。
12. 新版在当前仓库内全新重写，不兼容旧版代码、数据和插件，完成后覆盖旧实现或先将旧版改名保留。
13. 插件采用 `lemon_js_extensions` 的混合插件模式，首版优先支持本地安装统一插件包。
14. 音乐 API 的业务语义尽量延续现有设计；Dart 业务层使用类型明确的接口，字符串 export 调用只保留在 Lemon JS 协议适配边界。
15. 音频使用封装好的 MPV 播放器，接入 `lemon_audio` 统一处理系统媒体能力；MixMusic 保留业务队列和音源调度职责。
16. 本地数据库是核心能力，但具体库后定；选型重点是查询、关系、批量替换、事务和迁移，同时保持 API 简单。
17. 首批支持 Android、Windows 和车机；其他现有 Flutter 平台随后支持，鸿蒙最后评估。
18. 收藏支持平台、本地或同时收藏；普通点击使用全局默认，长按或首次弹窗选择，初始默认暂定为当前平台。
19. 歌词确定使用本地 `lemon_lyric`；普通、逐字和翻译等功能已经具备，正式接入前重点解决 Apple Music 风格渲染与动画造成的卡顿。

## 10. 待决定事项

- 首版是否开放音源以外的通用插件能力。
- 播放终端插件的运行边界及协议。
- 是否允许插件完整替换播放页面。
- UI 扩展采用页面、插槽还是两者结合。
- WebDAV 由宿主内置还是作为同步插件提供。
- 本地音乐是否进入新版首发范围。
- 平台收藏是否支持双向同步。
- 评论首版只读还是同时支持交互。
- 多账号模型和账号切换方式。
- 动态对象 ID 包含临时字段时如何生成稳定内部索引。
- 是否正式支持裸单文件 JS 插件；若支持，是否仅在安装时自动包装为统一 manifest 插件包。
